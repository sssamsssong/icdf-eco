# 시연 가이드 (2026 Energy ICDF 부스)

부스에서 시연을 켜고, 보여 주고, 설명하고, 끄는 방법입니다.
처음 맡는 팀원도 이 문서만 보고 진행할 수 있게 썼습니다.

## 한눈에 보기

- 영국 전력망의 **하루(24시간)를 2분**으로 빠르게 재생합니다. 화면 시계 1시간 = 5초.
- 같은 작업, 같은 마감, 같은 탄소 신호를 두 랙에 똑같이 줍니다. **스케줄러만 다릅니다.**
  - **B 랙** (왼쪽): 하루 전에 세운 계획을 그대로 실행 (구글 방식)
  - **D2 랙** (오른쪽): 예측이 계속 틀릴 것 같을 때만 계획을 고침 (우리 방식)
- 팬 하나 = 돌아가는 AI 작업 하나. 팬이 돌면 그 시간에 작업을 하고 있다는 뜻입니다 (냉각용 아님).
- 가운데 LED 바 = 지금 전력망의 탄소 집약도. 초록 = 깨끗함, 빨강 = 탄소 많음.
- **구름 버튼** = "예보에 없던 구름이 와서 태양광이 줄었다"는 상황. 탄소 값이 갑자기 올라갑니다.

## 1. 켜기 (부스 열기 전, 10분)

1. 전원: 팬 12V 어댑터, LED 5V 어댑터, (쓰는 경우) Jetson 2대, 스위치
2. 아두이노 USB를 메인 PC에 꽂기
3. 터미널을 열고:
   ```bash
   cd ~/icdf-eco
   source .venv/bin/activate
   python -m controller.main --day 2025-03-10 --ours --gui --port /dev/ttyACM0
   ```
   Jetson까지 쓰면 끝에 `--jetson-b http://10.0.0.11:8100 --jetson-d2 http://10.0.0.12:8100`를 붙입니다.
4. 브라우저가 자동으로 열립니다 (안 열리면 http://127.0.0.1:8000/). **F11**로 전체 화면. 글자가 작으면 Ctrl + 마우스 휠.
5. 점검:
   - [ ] 화면 아래에 `아두이노 /dev/ttyACM0` (Jetson을 쓰면 `Jetson B 연결됨, D2 연결됨`)
   - [ ] [시작]을 한 번 눌러 팬 4개, LED가 화면과 같이 움직이는지 보고, 끝까지 돌리거나 다시 시작
   - [ ] 리허설에서 정한 람다 값이 화면 아래(`람다 __ g`)에 맞게 표시되는지

## 2. 조작법

| 하고 싶은 것 | 화면 | 키보드 (브라우저 창에서) |
|---|---|---|
| 하루 재생 시작 / 다시 시작 | [시작] / [다시 시작] | Enter |
| 구름 올리기 / 걷기 | [구름 올리기] / [구름 걷기] | 스페이스 |
| 엔진 끄기 | | 터미널에서 Ctrl+C |

- 재생 중에는 [시작]이 잠깁니다. 하루가 끝나야 [다시 시작]을 누를 수 있습니다.
- 구름은 칸(30분)이 바뀌는 순간에 반영됩니다. 누르고 최대 2.5초 뒤에 그래프에 나타납니다.

## 3. 화면 읽는 법

| 위치 | 내용 |
|---|---|
| 왼쪽 위 그래프 | 점선 = 하루 전 예측, 실선 = 실제 탄소 값, 붉은 띠 = 구름이 있던 시간 |
| 왼쪽 아래 작업 일정 | 랙마다 48칸 x 2줄(팬 두 개). 진한 칸 = 이미 실행, 옅은 칸 = 예정. **주황 테두리 = D2가 옮겨 온 작업, 주황 점선 = D2가 비운 자리** |
| 오른쪽 위 누적 탄소 | 두 랙이 지금까지 배출한 탄소(g), 팬 상태, 계획 변경 횟수, 두 랙 차이 |
| 오른쪽 아래 | D2가 언제 어떤 작업을 몇 시로 미뤘는지, 예상 이득 |

## 4. 보여 줄 장면 (2025-03-10 기준)

이 날은 **새벽 00:00 ~ 04:00**에 유연한 작업이 몰려 있습니다. 구름은 이 시간에 올려야 차이가 보입니다.
화면 시계 기준으로 00:00 → 02:00까지 10초, 04:00까지 20초 걸립니다.

**장면 1: 짧은 구름 → 두 랙 모두 그대로** (1회차)
1. [시작]
2. 시계가 **03:00**이 되면 구름 올리기, **03:30** 근처에서 바로 걷기 (1시간 이하)
3. D2도 계획을 바꾸지 않습니다. "잠깐 지나가는 구름에 계획을 흔들지 않는다"가 포인트.
4. 하루가 끝나면 두 랙 누적 탄소가 같습니다.

**장면 2: 긴 구름 → D2만 작업을 미룸** (2회차)
1. [다시 시작]
2. 시계가 **02:00**쯤 구름 올리기, **05:00**이 넘으면 걷기 (2시간 이상)
3. 구름이 두 시간째 이어지는 **04:00**에 D2가 그 칸의 작업 두 개(`train-1`, `batch-2`)를 밤 21:30으로 미룹니다.
   B 팬은 그대로 도는데 **D2 팬 두 개만 멈추는** 순간이 하이라이트입니다. 오른쪽 아래에 변경 기록이 뜹니다.
4. 하루가 끝나면 D2가 B보다 약 5% 덜 배출합니다 (람다 20 기준).

> **주의: 람다 값에 따라 장면 1이 달라집니다.** 지금 `controller/config.py`의 `LAMBDA_G`는 **10**인데,
> 10에서는 30분짜리 구름에도 D2가 계획을 바꿔서 장면 1이 성립하지 않습니다. 2026-11-18에 미리 돌려 본 결과:
>
> | 람다 | 30분 구름 | 1시간 구름 | 2시간 구름 | 3시간 구름 | 5시간 구름 |
> |---|---|---|---|---|---|
> | 10 (지금) | 2회 변경 | 4회 | 4회 (-10.4%) | 6회 (-14.8%) | 8회 (-17.8%) |
> | 15 | 0회 | 2회 | 2회 (-5.1%) | 2회 (-4.9%) | 2회 (-4.6%) |
> | **20 (추천)** | **0회** | **0회** | **2회 (-5.1%)** | **2회 (-4.9%)** | **2회 (-4.6%)** |
> | 30 이상 | 0회 | 0회 | 0회 | 0회 | 0회 |
>
> 구름은 각각 03:00, 03:00~03:30, 02:30~04:00, 02:00~04:30, 01:00~06:00. 괄호는 B 대비 D2 배출 차이.
> 리허설에서 람다를 정하고 `config.py`의 `LAMBDA_G`를 바꾸세요. 20이면 짧은 구름/긴 구름 장면이 깔끔하게 나뉩니다.

**관람객이 아무 때나 구름을 누르면?**
- 작업이 없는 시간(04:30~10:30 등)에 누르면 두 랙 모두 달라지는 게 없습니다. 돌릴 작업이 없으니까요.
- 낮(11:00~13:30)에 누르면 D2도 대부분 옮기지 않습니다. 그 뒤 시간이 더 더러워서 옮길 이득이 없기 때문입니다. "무조건 미루는 게 아니라 이득이 있을 때만"이라고 설명하면 됩니다.

**버튼 타이밍이 불안할 때 (자동 구름)**
```bash
python -m controller.main --day 2025-03-10 --ours --gui --port /dev/ttyACM0 --cloud 4-9
```
`--cloud 4-9`는 칸 번호로 4~9번 칸(02:00~05:00)에 자동으로 구름을 겁니다. 칸 번호 = 시각 x 2.
**이때는 구름 버튼이 동작하지 않습니다.** 짧은 구름 장면은 `--cloud 6-7`.

## 5. 설명 대본

**30초 버전 (지나가는 관람객)**
> "AI 데이터센터는 전기를 많이 씁니다. 그런데 같은 전기도 바람이 불고 해가 날 때 쓰면 탄소가 훨씬 적어요.
> 그래서 급하지 않은 AI 작업은 깨끗한 시간으로 미루는데, 문제는 날씨 예보가 틀릴 때입니다.
> 왼쪽은 구글처럼 하루 전 계획을 그대로 지키고, 오른쪽은 저희 방식이에요. 구름 한번 올려 보시겠어요?"

**2분 버전 (심사위원)**
1. 문제: 탄소 인지 스케줄링은 구글이 이미 하고 있다. 하지만 하루 전 예측에 의존하고, 예측이 틀려도 계획을 고치지 않는다.
2. 반대로 매 순간 다시 계획하면 일정이 계속 흔들려서 운영이 어렵다.
3. 우리 방식: 계획은 유지하고, **오차가 계속 이어질 것 같고** 옮기는 **이득이 변경 비용(람다)보다 클 때만** 고친다.
4. 시연: 짧은 구름 → 그대로 / 긴 구름 → D2만 미룸 (장면 1, 2)
5. 근거: 실제 영국 데이터 685일 시뮬레이션. 매번 다시 계획하는 방식보다 **변경은 절반**(하루 2.4회 vs 4.1회)인데, 예측 오차로 놓친 탄소는 **비슷하거나 더 많이 회복**(9.6% vs 8.9%).
6. 한계도 같이: 영국 데이터 기반, 탄소는 추정치, B 대비 절대 감소는 0.5% 정도로 아직 작음.

**자주 받을 질문**

| 질문 | 답 |
|---|---|
| 시연에서는 5%인데 시뮬레이션은 왜 0.5%? | 부스의 구름은 크고 갑작스럽게 만든 상황입니다. 실제 하루하루의 예측 오차는 대부분 작아서 평균 효과는 작습니다. 저희가 내세우는 건 **적은 변경으로 비슷한 회복**이라는 점입니다. |
| 왜 매번 다시 계획하지 않나? | 실제 데이터센터는 작업이 자주 옮겨지면 자원 예약, 사용자 약속이 흔들립니다. 그 비용을 람다로 넣었습니다. |
| 람다가 뭔가? | 계획을 한 번 바꾸는 데 드는 "비용"을 탄소 g으로 적은 값. 옮겨서 줄어드는 탄소가 이보다 커야 옮깁니다. |
| 오차가 이어질지는 어떻게 아나? | 2024년 데이터로 "최근 4시간 오차를 보면 몇 시간 뒤 오차가 얼마인지" 학습했습니다. |
| 급한 작업은? | 긴급 작업(`urgent`)은 절대 옮기지 않고, 마감도 항상 지킵니다. |
| 전력은 실제로 잰 건가? | 화면의 큰 숫자는 작업당 가정 전력량으로 계산합니다. Jetson을 연결하면 실측 전력과 실측 탄소가 랙 카드에 따로 표시됩니다. |
| 한국에도 되나? | 영국 데이터로만 검증했습니다. 한국 전력망 데이터로는 따로 확인해야 합니다. |

## 7. 문제가 생기면

| 증상 | 해결 |
|---|---|
| 화면에 "엔진 연결 끊김" | 터미널의 엔진이 꺼졌음 → 1번의 실행 명령 다시 |
| 엔진이 `Permission denied`로 안 켜짐 | [아두이노_연결후_할일.md](아두이노_연결후_할일.md) 1번 |
| `Device or resource busy` | 엔진이 이미 켜져 있거나 시리얼 모니터가 열려 있음 → 닫고 다시 |
| `Address already in use` | 엔진이 이미 켜져 있음 → 다른 터미널 확인, 또는 `--http-port 8001` |
| 팬이 안 멈춤 | 엔진을 Ctrl+C로 끄면 꺼짐. 그래도 안 되면 아두이노 USB 뽑았다 꽂기 |
| 하드웨어가 다 안 될 때 (비상) | `--port` 대신 `--dry-run`으로 화면만 켜서 설명 |
| 화면이 너무 빠르게/느리게 느껴짐 | `--slot-seconds 3` (하루 2분 24초), 리허설 때는 `--slot-seconds 0.5` |
